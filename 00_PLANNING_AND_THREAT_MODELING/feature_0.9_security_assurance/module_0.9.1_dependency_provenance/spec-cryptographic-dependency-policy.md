# Cryptographic dependency provenance and vector gate

## 1. Metadata

- **Specification ID:** G06
- **Version:** 1.0
- **Owner:** p2p-offramp maintainers
- **Status:** Expanded design baseline — implementation and independent review pending
- **Delivery phase:** 0
- **Reviewed source baseline:** docs/security-spec-expansion-20261021
- **Normative language:** MUST is a release gate; SHOULD deviations require a recorded reason.

## 2. Objective

Make primitive/provider selection reproducible and reviewable before enabled capabilities depend on it. A version pin is provenance evidence, not an audit. Core G02 uses browser-native AES-GCM/PBKDF2; advanced circuit, Nostr, and chain libraries are not approved merely because their names appear in a spec.

## 3. Architecture and inventory

The implementation adds `security/crypto-inventory.json`, a runtime lockfile, and version-controlled vector fixtures. Each enabled capability references approved inventory entries; disabled candidates remain separate and cannot pass release checks by inheriting another library's review.

```typescript
interface CryptoDependency {
  id: string;
  capability: string;
  primitive: string;
  sourceUrl: string;
  version: string; // exact release/commit, or built-in browser profile
  integrity: string; // lockfile integrity or vendored source SHA-256
  license: string;
  runtime: "browser-built-in" | "npm" | "vendored";
  review: { status: "pending" | "accepted" | "rejected";
            reviewer: string; evidencePath: string };
  vectors: readonly { path: string; sha256: string; provenanceUrl: string }[];
}
```

Fields are nonempty except reviewer/evidencePath while pending. `accepted` requires a named review and existing evidence file. Runtime browser built-ins use a versioned browser-support matrix plus executed vectors rather than an invented package hash. Inventory is public build metadata and contains no keys, signed messages, wallet addresses, or user endpoints.

## 4. Algorithms and selection rules

1. Inventory every directly or transitively used crypto implementation and its enabled feature. Pin exact package versions and a lockfile; use frozen-lockfile installs in CI. Vendored code records source commit, file hashes, local patches, license and attribution.
2. Before acceptance verify upstream ownership/source, license compatibility, maintenance/security history, implementation scope, and independent vector provenance. An upstream audit must name the exact evaluated version/configuration; unrelated audit reports do not transfer approval.
3. Hash fixture bytes with SHA-256. Run primitive KATs and invalid cases independently of higher-level protocol tests. Expected results MUST not be generated by the implementation under test. Native G02 requires PBKDF2-HMAC-SHA256 and AES-GCM interoperability and tamper tests, including exact 600000 iteration application profile tests.
4. A dependency update changes source/version/integrity/inventory/vector review in one reviewed change. Execute all dependent capability tests, review changed API/side channels/randomness, and regenerate reproducible artifacts. Do not automatically enable a formerly disabled provider after an update.
5. If review or vectors are missing, the affected feature stays disabled. CI distinguishes `candidate`, `test-enabled`, and `release-enabled`; only release-enabled entries require accepted review for release. Tests cannot claim a library is accepted merely by passing.
6. Rollback restores the previous full lockfile/inventory/artifact set. Never downgrade stored data formats or mutate funded escrow semantics to match an old package. Maintain read/recovery paths for supported earlier versions.

No package versions are selected in this spec: installation must evaluate current source and lock the actual choice. That implementation gate is explicit, not an unresolved API contract.

## 5. Interfaces and CI outcomes

`verifyCryptoInventory(inventory, lockfile, enabledCapabilities, fixtureFiles)` returns a list of fixed-code findings with paths, never secret payloads. Required finding codes: `UNPINNED_VERSION`, `INTEGRITY_MISMATCH`, `MISSING_LICENSE`, `MISSING_REVIEW`, `MISSING_VECTOR`, `FIXTURE_HASH_MISMATCH`, `UNDECLARED_CRYPTO`, `UNSUPPORTED_RUNTIME`. Any finding for a release-enabled dependency fails release CI. Missing test-only reviews produce a labeled pending report, not a passing production badge. Inventory schema rejects unknown fields, duplicate IDs, path traversal, missing evidence, and malformed hashes. Source/evidence URLs are informational and are never fetched/executed by the verifier. Report generation is deterministic and makes no network calls.

## 6. Threat assessment

Registry takeover, typosquatting, malicious install scripts, mutable release tags, compromised transitive code, and forged vectors are distinct risks. Verify source and locked content, minimize dependencies and install scripts, review transitive diffs, and run builds with minimal credentials. SRI/hash equality proves bytes match a chosen artifact, not that it is safe. Runtime Web Crypto behavior depends on the actual browser/OS; record browser versions and test evidence. Known-answer tests alone do not prove side-channel resistance, secure randomness, protocol correctness, or whole-product security.

## 7. Verification and references

Unit fixtures MUST cover each finding code, duplicate IDs, missing evidence files, malformed hashes, absolute/escaping paths, URL-only evidence, and candidate-versus-enabled distinction. A test mutating one vector byte must fail hash validation before tests run. A transitive crypto package absent from inventory must fail the declared implementation graph review. Run clean offline/frozen installs from a verified cache and compare artifact hashes across two clean builds. Include a fixture produced by a separate implementation for every enabled primitive and protocol suite. Record which checks remain manual; automated detection of all crypto use is not assumed.

Primary sources: [Web Crypto Recommendation](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/), [NIST CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program), [RFC 8018](https://www.rfc-editor.org/rfc/rfc8018), and exact upstream sources pinned by the implementation inventory.
