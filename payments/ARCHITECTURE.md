# Custodial P2P payments — separate architecture track
**Status:** prototype foundation; NOT production ready, not licensed for real money. This architecture differs fundamentally from the non-custodial crypto off-ramp specifications in the repository. Do not connect this ledger to escrow or accept real customer funds without an explicit product/operating-model decision and legal review.

## Stack and boundaries
Backend Node.js 22 LTS + TypeScript + Fastify (planned); PostgreSQL 16+ authoritative ACID ledger; Redis optional for ephemeral rate-limit cache only, never balances; transactional outbox for event delivery; background workers for payment provider adapters; WebSocket/SSE status from committed outbox; React/Vite web app and responsive PWA with WalletConnect/QR integration only if relevant. Auth: OIDC with short-lived sessions, secure cookies, CSRF, MFA and device binding; service-to-service mTLS and HMAC signed provider webhooks. KYC/AML: simulation only in test environments; production needs licensed regulated providers, sanctions screening, case management, record retention and jurisdiction-specific counsel.

## Component map
Client -> authenticated API -> transfer service -> PostgreSQL serializable ledger transaction -> outbox -> notification worker. Separate bounded services: identity, contacts/discovery, ledger, transfer orchestration, funding and cash-out adapters, risk/compliance, dispute/chargeback and reporting. External payment processors are untrusted asynchronous systems; their webhooks never directly mutate wallet balances without idempotent ledger posting and verification.

## Ledger rules
All money in integer minor units (currency exponent defined by ISO 4217 registry; no floats). Each journal has >=2 entries, sum(debits) == sum(credits) by currency, immutable after posting. Accounts carry one currency and class (ASSET, LIABILITY, REVENUE, EXPENSE, EQUITY). Customer available balance is computed from posted ledger movements and held liabilities, not Redis. Every movement posts atomically with idempotency claim and transactional outbox event. No negative spendable wallet balances. Holds reserve available funds before asynchronous settlement; capture/release transitions are atomic, exclusive and replay safe. Reversals are new compensating journals, never edits. Payment processor pending settlement is not customer cash until verified according to rail-specific policy.

## API and frontend contract (planned)
POST /v1/transfers {recipientId, currency, amountMinor, idempotencyKey}; GET /v1/transfers/:id; GET /v1/wallets/:id/balance; POST /v1/holds; POST /v1/funding-intents; POST /v1/cashouts; POST /v1/webhooks/:provider with verified signature; GET /v1/events (SSE). All mutating APIs require authenticated actor, authorization, idempotency and replay protections. Responses include immutable IDs, state, server timestamp, trace ID and safe error codes. Frontend: send/request, contacts, wallet dashboard, transaction history, QR sharing and receipts; accessibility WCAG 2.2 AA, responsive mobile and localization.

## Phases and gates
P1 PostgreSQL schema, immutable journal posting, holds, reconciliation and tests. P2 identity/session and risk policy, contact discovery, transfer API, concurrent transfers and outbox. P3 simulated bank/card funding, cash-out, webhook verification, notifications, fraud and disputes. P4 web/mobile UI, QR, accessibility and browser testing. P5 deployment IaC, observability, backups, DR, independent security review, penetration test and regulatory approval. No production claim until 0 drift under concurrency/fault injection, independent ledger reconciliation, complete threat model, approved KYC/AML program, PCI scope assessment, incident response and licensed partner agreements.

## Failure and threat cases
Duplicate HTTP retries, parallel spends, deadlocks, transaction aborts, chargebacks, stale caches, webhook replays, processor partial failures, lost outbox events, identity takeover, malicious insider and database restoration. Use serializable isolation, consistent lock ordering, bounded retry on SQLSTATE 40001/40P01, account authorization, immutable audit and reconciliation jobs. Payment-card data must never enter application logs or database; use provider-hosted tokenization. No user-supplied arbitrary SQL identifiers or floating-point amounts.
