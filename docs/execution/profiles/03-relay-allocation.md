# Nostr incremental inbound allocation

Decision: retain the honest direct-browser limitation. No maintained, reviewed alternative Nostr incremental profile was established by this bounded source review. This is not an exhaustive absence claim.

Primary pins: [NIP-01](https://github.com/nostr-protocol/nips/blob/400d157c53264b8e58c7b3cdbd21ef546fb7a157/01.md), [NIP-11](https://github.com/nostr-protocol/nips/blob/400d157c53264b8e58c7b3cdbd21ef546fb7a157/11.md), [indexed NIPs](https://github.com/nostr-protocol/nips/blob/400d157c53264b8e58c7b3cdbd21ef546fb7a157/README.md); [WHATWG WebSocket](https://github.com/whatwg/websockets/blob/7f25d7dc8c2598ebca795ce4af68909d913a3888/index.bs).

NIP-01 uses WebSocket endpoints and JSON-array messages. WHATWG fires `message` after a WebSocket message has been received and constructs a DOMString/Blob/ArrayBuffer containing its data. The API exposes neither raw fragment reads nor an inbound preassembly byte cap. `binaryType='blob'`, a Worker or size-checking `event.data` does not turn this into an adversarial preallocation guarantee. A streams wrapper/backpressure alone does not establish a message-size cap either.

The repo already documents this at `packages/relay/src/pool.ts:10`; its65536-byte frame/event parser cap and tag/count bounds limit parse/crypto work after delivery. This remains valuable engineering, with existing pool lifecycle/URL/native-crypto tests. It must not be relabeled as a network-memory cap. NIP-11 `max_message_length` is a relay-advertised server limitation on incoming client JSON, not authenticated enforcement against a malicious relay sending huge data to the client.

Concrete maintained alternative to evaluate locally, without inventing Nostr messages: Node `ws` receiver snapshot [`f40ccff`](https://github.com/websockets/ws/blob/f40ccfff97bbdea2eba574ecd6c1ba88156c73c3/lib/receiver.js) exposes maxPayload/maxFragments/maxBufferedChunks and checks accumulated payload and decompressed lengths. This is source-level candidate evidence, not an installed/evaluated dependency or a whole-process memory proof. A native companion can enforce bounded upstream WS messages before forwarding unchanged NIP-01 to the browser. It creates a new explicitly trusted/authenticated companion boundary; direct hostile browser peers remain unbounded by the browser API. TCP/TLS/native buffers and compression still need measured/adversarial tests.

Ready next experiment: choose a pinned receiver package/lock and native test-only companion, enforce65536-byte message cap plus explicit fragment/chunk/connection budgets, disable or separately cap compression, authenticate the local hop, fail closed on oversized/header-only/fragmented/decompression floods, and prove cancellation/disposal/owned socket cleanup. This needs no real relay account or funds and must remain opt-in. Do not claim browser-global enforcement or route privacy.

Unselected protocol choices: companion packaging/authentication/current-scope evidence, endpoint and G05 ownership, supported browser/OS targets and failure policy. HTTP/NDJSON, WebTransport or custom chunked application envelopes would be distinct negotiated protocols; no reviewed Nostr interoperability contract for them was found among these sources. Do not silently replace NIP-01 or invent such a profile just to mark the task complete. A trusted server promising small messages is not a client-enforced bound.
