# G26 local incident and recovery preparation

This is a checklist, not a performed drill or an actual IncidentRecord. No support channel, incident, affected release, reviewer, advisory digest or publication is invented. Imported IncidentRecord severity/reviewer/status fields are attributed intake claims; validation cannot establish containment, authorization, review or closure. Random incident IDs must be generated independently of people, wallets and trades. No private operational record belongs in this public packet.

1. Record only a public release/manifest sequence, module/fixed error code/operation, chain namespace, storage schema and approximate UTC time. State fund risk as yes/no/unknown; separate facts from hypotheses. Use G26's existing severity definitions, choose the higher level when uncertain, then document triage. Never request or copy keys, passphrases, seed phrases, wallet/trade identifiers, amounts, bank details, messages, locations or trade screenshots into diagnostics or a public incident.
2. Preserve the affected public source/release hashes and deployment IDs when actually known. Use `packages/diagnostics/index.ts` and its existing collect/preview/clear interface for explicit local selection and final-byte preview. Diagnostics are a bounded local ring, not an audit ledger or complete redaction guarantee. No automatic upload or contact action is performed. The user decides separately whether and where to share a downloaded export; a maintained verified channel is an external G26 requirement.
3. Reproduce only using owned public synthetic fixtures/local chains. Existing diagnostics regressions: `node --import ./scripts/test-support/register-tsx.mjs --test packages/diagnostics/test/diagnostics.test.mjs`. This tests allowlists, secret-string refusal, age/count limits, corrupt storage, locked clear and revocation; a passing unit suite is not an operational incident drill.
4. Build a scoped acceptance report with the existing `npm run acceptance:report -- candidate.json records.json` interface documented in `docs/OPERATOR.md`, selecting local evidence inputs. Report generation and imported `passed`/reviewer labels are not evaluator authority. Preserve exact artifacts and their hashes. Existing static admission/build checks can identify changed graph/bytes but cannot authenticate an uncompromised signing root or professional review.
5. Keep existing immutable basic-escrow exits available. A later advisory may disable new funding in a signed higher-sequence release; this checklist performs no advisory publication, endpoint removal, signature or remote action. Maintainers cannot pause/reverse canonical settlement or repair fiat loss. Signing-root compromise requires separately verified out-of-band recovery, not an unsigned same-origin key replacement.
6. Inspect existing offline recovery with the built original-pin recovery bundle and `docs/recovery/CANONICAL-EVM.md` inspect/prepare flow (`scripts/recovery/evm-cli.mjs` is the source entry, not a standalone configured bundle); independently confirm chain/genesis, admitted deployment/code, exact trade binding, current wallet/role, native time/state, canonical/finalized anchors and fixed recipient. Use the existing read-only recovery preparation and reference import/validation flow; unknown transaction outcome remains unresolved until native reconciliation. Do not infer a successful send or initiate a second economic intent. This packet initiates no recovery transaction.
7. Local negative recovery regressions are `node --import ./scripts/test-support/register-tsx.mjs scripts/tests/evm-recovery.test.mjs`. The repository's `npm run test:recovery:evm` adds its pinned owned-loopback native harness. Use the evaluated toolchain/environment and explicit local fixture; these commands provide engineering evidence, not static-origin/IPFS outage qualification or real-wallet acceptance.
8. A real drill must separately record exact source/release/deployment revisions, known/unknown impact, recovery observations, redacted evidence, failed steps, reviewer decision and postmortem changes. Bad release, compromised endpoint, signing-root incident and lost origin each need their own actual bounded exercise. Until done, report them as missing. No timeline, compensation, fund-safety or specific recovery outcome is promised.

Actual legal applicability, named professional review, maintained security contact, static-origin/IPFS recovery availability, human incident ownership and device/physical acceptance remain external evidence. Their absence is explicit; local validation and preparation do not fabricate approval.
