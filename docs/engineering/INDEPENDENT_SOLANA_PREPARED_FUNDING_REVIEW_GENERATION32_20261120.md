## Design and implementation review

The new `prepareFunding(trade, sellerSession, options?)` is a distinct native capability. The existing `PreparedSolanaActionKind`, exit-only `prepare()` behavior and its explicit refusal of `fund` remain intact. Direct `fund()` behavior is unchanged. `PreparedSolanaFunding` narrows the visible action to funding, role to seller, expected escrow state to absent and shape to the funding variant, while retaining the existing private brand. The actual authority remains in the original per-client `WeakMap`; copies, serialization and views owned by another client confer no confirmation or cancellation authority.

Funding options are captured synchronously before queueing or asynchronous work. Only the two named own data properties are accepted. A supplied seller source must be a bounded canonical 32-byte base58 key, and a supplied replacement must satisfy the existing intent-ID parser. Accessors, symbols, unknown keys and non-plain objects are rejected without evaluating property getters. A frozen scalar copy is retained by the planner closure, so later caller mutation cannot alter either the prepared bytes or subsequent eligibility checks. The original SPL planner still selects its default ATA when no source override is supplied; preparation adds no claim that a supplied source account is program-owned or executable.

The private preparation overload selects existing `planFund`, which enforces the seller, absent-escrow/funding-window and existing asset policy constraints. The original preparation path validates the owned connected session and complete binding, performs fresh finalized reads, persists the exact transaction message and original blockhash, and checks active profile/session authority again before publishing the immutable view. The review exposes frozen binding and shape snapshots backed by the retained journal record.

The bodies of confirmation and cancellation are unchanged. Confirmation consumes the private capability synchronously and keeps the original physical serialization slot while it reloads the journal, checks exact retained identity and bytes, revalidates the original blockhash, and replans against fresh finalized state. The same path repeats eligibility, deployment, wallet/session, profile and blockhash checks after a delayed wallet response before a durable send marker can be made. The existing wallet boundary verifies the exact message and signature. Cancellation revokes immediately but cannot release a pending physical wallet prompt's slot before settlement or retract a marked/submitted intent.

Existing journal compare-and-swap and uncertain-write behavior are retained. A changed persisted record cannot replace the privately retained preparation or be cancelled as though it were the original. Uncertain sends remain recoverable without automatic retransmission. Cross-client and restored-profile records do not regain signing authority; a definitive drop requires the existing explicit replacement path. The real encrypted journal lock case is covered by the maintained fixture alongside controlled journal/RPC/provider cases.

The [wallet-provider specification](../../01_P2P_SHIELDED_OFFRAMP_ENGINE/feature_1.6_wallet_connectivity/module_1.6.1_provider_boundary/spec-wallet-provider-interface.md) requires explicit initiation, durable exact requests and current-session checks; [accepted D5](../adr/ACCEPTED-DECISIONS-2026-11-04.md) defines seller-funded native SOL/original SPL and finalized custody observations. The implementation respects that additive scope. The separate reconnaissance message identified the intentionally exit-only preparation contract and the recovery browser's already-funded requirement. Those are preserved contracts, not defects. No new mint, program, production trust, endpoint, default activation or release approval is added.
