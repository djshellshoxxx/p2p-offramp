# Reuse research: payment evidence, stealth, reputation and arbitration

Research completed 2026-11-04 UTC for the 2026-11-03 research batch. This is source review and an integration map, not an adoption record or provider qualification.

## Recommendation and source scope

The reviewed source snapshot is PR #26 at `94554ecf9854e4604f9f56afe5bebedeee931994`; the research coordinator independently matched all 653 tracked source/test/config blobs to that remote commit. Pins identify inspected source, not reproduced release artifacts. Root project licensing remains unresolved: the reviewed remote tree has no root `LICENSE`. ## Payment evidence: exact code, missing glue and acceptance

### TLSNotary core and the current browser client

The useful verifier source is [`crates/attestation/src/presentation.rs`](https://github.com/tlsnotary/tlsn/blob/24b10ba21bf36c3fd3de709e7eccd8308bb64207/crates/attestation/src/presentation.rs). `Presentation::verify()` returns an attestation, connection information, and **optional** authenticated server name and transcript. A receipt adapter must require its necessary fields. The library documents that the verifier must trust the attestation signing key. The inspected [`crates/examples/attestation/verify.rs`](https://github.com/tlsnotary/tlsn/blob/24b10ba21bf36c3fd3de709e7eccd8308bb64207/crates/examples/attestation/verify.rs) uses a fixture certificate store for offline testing; that fixture root is not a production trust policy. Its transcript-printing behavior is also unsuitable for private bank evidence logs.

The current browser boundary is in `tlsn-extension`. Inspected [`packages/plugin-sdk/src/types.ts`](https://github.com/tlsnotary/tlsn-extension/blob/d44623434d04ad00d7b1f8da9712cbc10cd0e99c/packages/plugin-sdk/src/types.ts), [`src/index.ts`](https://github.com/tlsnotary/tlsn-extension/blob/d44623434d04ad00d7b1f8da9712cbc10cd0e99c/packages/plugin-sdk/src/index.ts), and [`packages/extension/src/offscreen/ProveManager/index.ts`](https://github.com/tlsnotary/tlsn-extension/blob/d44623434d04ad00d7b1f8da9712cbc10cd0e99c/packages/extension/src/offscreen/ProveManager/index.ts) expose reveal/hash handlers, request permissions, QuickJS-related plugin infrastructure, and an offscreen Worker plus verifier WebSocket sessions. The official [browser quick start](https://tlsnotary.org/docs/quick_start/browser_extension/) identifies a Chromium extension and verifier server. These observations do **not** establish that the reviewed core/client commits form a compatible version pair. The archived `tlsn-js` package is historical only and should not be the implementation target.

**Destination:** the proof-input provider adapter should normalize authenticated results into a versioned advisory statement. A Rust/WASM verifier bridge, if chosen, could occupy **NEW** `packages/proof-jobs/providers/tlsn-verifier/` behind the existing supervisor. Extension communication belongs in a separately reviewed external-client adapter, not generic receipt parsers. The permitted client/service architecture must decide the packaging.

**Missing glue:** exact core/client/verifier pairing; artifact hashes; trusted-notary key lifecycle; expected source origin and request identity; canonical response parsing; complete necessary disclosures; trade/challenge/amount/currency/recipient/status/freshness binding; replay store; credential isolation; minimal failure reports. A source reporting a transfer as sent or pending cannot be interpreted as irrevocable receipt, and a TLS proof cannot establish receipt of physical cash.

**Acceptance:** independent valid/malformed fixtures; reject wrong notary, origin, challenge and trade; reject omitted or mismatched beneficiary, currency, amount and status; review minimal disclosure; demonstrate that partial transcripts cannot qualify by omitting necessary fields; keep credentials and transcript bytes out of logs; document extension/mobile availability and disconnections. None of these runtime outcomes is established by this source review.

### Reclaim SDK and attestor-core have different roles and licenses

Useful SDK entry points in [`src/Reclaim.ts`](https://github.com/reclaimprotocol/reclaim-js-sdk/blob/a483dda82e2a2437d93571351c2d7f608182fdd5/src/Reclaim.ts) include `ReclaimProofRequest.initWithSignature()`, `fromJsonString()`, `getProviderVersion()` and `verifyProof(proof, config)`. The alternative `init(applicationId, appSecret, ...)` consumes an application signing secret. Do not copy that secret-bearing initialization into the static web app. `initWithSignature()` accepts externally produced authorization and, when TEE attestation is enabled, an attestation-nonce callback. An external signing authority/backend must be an explicit architecture decision, not silently added to make a sample work.

[`src/utils/proofValidationUtils.ts`](https://github.com/reclaimprotocol/reclaim-js-sdk/blob/a483dda82e2a2437d93571351c2d7f608182fdd5/src/utils/proofValidationUtils.ts) distinguishes explicit expected hashes from provider/version content requirements. A qualified profile must freeze the required checks and prevent proof-supplied options from weakening them. The inspected verifier documentation leaves replay tracking to the caller. Provider-version resolution may depend on network state; a moving latest version is not an adequate semantic contract.

**Destination:** **NEW** `packages/proof-inputs/src/providers/reclaim.ts` for strict statements and **NEW** `packages/proof-jobs/src/providers/reclaim.ts` for session/job lifecycle. Keep application signing secrets outside the bundle and generic witness model. Trusted profile configuration must bind expected provider version/hash, initiated session/challenge, witness/attestor rules and any TEE requirements. Restore a request object only after authenticating its provenance; JSON import alone grants no authority.

The inspected lower-level claim path, [`attestor-core/src/server/utils/assert-valid-claim-request.ts`](https://github.com/reclaimprotocol/attestor-core/blob/dd43dc882b88dcfe75d27a1c1a991315574823ab/src/server/utils/assert-valid-claim-request.ts), is useful for understanding attestor validation. Its AGPL terms require a decision separate from the MIT SDK. Server validation/service availability do not provide this application's receipt semantics, replay journal or payment finality policy.

**Acceptance:** reject another initiated session, unapproved version/statement hash, stale or repeated receipt, wrong beneficiary or amount; cover attestor-set changes and service outages; verify absence of application secrets from shipped bundles and logs; document mandatory TEE checks if selected; review the entire installed dependency graph. The organization MIT license is necessary evidence, not a blanket compatibility clearance.

### vlayer and ZK Email: narrower reference value

[`vlayer/contracts/vlayer/src/WebProof.sol`](https://github.com/vlayer-xyz/vlayer/blob/25197319a041935efbb09b8cbc57ba123702aaab/contracts/vlayer/src/WebProof.sol) contains `WebProofLib.verify()`, URL-prefix verification, notary-key checks, redaction modes and a specialized verification precompile call. It illustrates the need to bind URL and notary policy. Its BSL terms, UNLICENSED header and specialized execution environment make it unsuitable as an immediate unrestricted dependency. Map these observations to proof-policy tests; do not import the contract merely because its source is public.

ZK Email's [`packages/helpers/src/input-generators.ts`](https://github.com/zkemail/zk-email-verify/blob/066c8742a5e60519597697e579333b703ffa6ad2/packages/helpers/src/input-generators.ts) exports `generateEmailVerifierInputs()` and `generateEmailVerifierInputsFromDKIMResult()`. [`packages/circuits/email-verifier.circom`](https://github.com/zkemail/zk-email-verify/blob/066c8742a5e60519597697e579333b703ffa6ad2/packages/circuits/email-verifier.circom) has configurable body checking/masking. [`packages/contracts/DKIMRegistry.sol`](https://github.com/zkemail/zk-email-verify/blob/066c8742a5e60519597697e579333b703ffa6ad2/packages/contracts/DKIMRegistry.sol) includes owner-controlled key registration/revocation. These add email-format semantics and DNS/DKIM key-history/registry trust.

If a selected rail has suitable signed receipts, evaluate **NEW** `packages/proof-inputs/src/providers/zk-email.ts` as advisory evidence only. Require authenticated body fields, signed-header coverage, accepted DKIM domain/key history, expiry, transaction identifier, trade binding and a receipt nullifier. A valid bank/merchant email does not establish that funds remain available. Circuit/toolchain dependencies, proving keys and setup provenance still need intake; they were not fully license-qualified here. This path should not delay a concrete TLS evidence profile.

### Common proof-runtime qualification

The existing proof-jobs policy specifies 1 MiB input, 2 MiB output, 256 MiB WASM memory, 120-second wall limit, 15-second heartbeat, one job per tab without a queue, 8 MiB network budget and 256 messages. Cancellation retains the physical slot until the worker drains. A real provider must fit these limits or return for an explicit resource-policy change. Background artifact downloads, extension work and remote-service costs need separate accounting. These upstreams were not benchmarked against the limits.

The best next comparison is a shared fixture corpus for the same source/trade statement through TLSN and Reclaim: correctness, disclosure, external trust, distribution terms, artifact size and bounded shutdown. Keep `createProofJobs().providers` empty until one exact profile is qualified; registering a name does not complete proof support.

## Stealth: qualify the existing comparisons before live transport

ScopeLift's [`src/utils/crypto/generateStealthAddress.ts`](https://github.com/ScopeLift/stealth-address-sdk/blob/88bcc27c3b6163080ee18f330dfd6336dc8bd2e2/src/utils/crypto/generateStealthAddress.ts) calls Noble `getSharedSecret()` and hashes the returned bytes. Particularly useful scan sources are [`getAnnouncementsPageUsingSubgraph.ts`](https://github.com/ScopeLift/stealth-address-sdk/blob/88bcc27c3b6163080ee18f330dfd6336dc8bd2e2/src/lib/actions/getAnnouncementsUsingSubgraph/getAnnouncementsPageUsingSubgraph.ts) and [`scanAnnouncementsForUserUsingSubgraph.ts`](https://github.com/ScopeLift/stealth-address-sdk/blob/88bcc27c3b6163080ee18f330dfd6336dc8bd2e2/src/lib/actions/scanAnnouncementsForUserUsingSubgraph/scanAnnouncementsForUserUsingSubgraph.ts). Adapt the contracts into `pages.ts`/`store.ts` fixtures. A subgraph response remains an observation requiring authenticated chain/emitter/canonicality validation.

**Acceptance and remaining glue:** independently execute matching implementations under an explicit scheme; compare generation, matching, invalid-point and view-tag cases; authenticate chain and announcer bytecode; test duplicate/missing pages, stale snapshots, cancellation/resume and reorg rollback; commit cursor/candidates atomically. An independently executed ScopeLift release can be a test oracle after resolving its dependency lock; it is not automatic approval of local math.

## Reputation: membership is only one layer

Inspected Semaphore sources are [`packages/identity/src/index.ts`](https://github.com/semaphore-protocol/semaphore/blob/dbab5553c486a09d5e1042e5271e3316224cc176/packages/identity/src/index.ts), [`packages/group/src/index.ts`](https://github.com/semaphore-protocol/semaphore/blob/dbab5553c486a09d5e1042e5271e3316224cc176/packages/group/src/index.ts), [`packages/proof/src/generate-proof.ts`](https://github.com/semaphore-protocol/semaphore/blob/dbab5553c486a09d5e1042e5271e3316224cc176/packages/proof/src/generate-proof.ts), and [`verify-proof.ts`](https://github.com/semaphore-protocol/semaphore/blob/dbab5553c486a09d5e1042e5271e3316224cc176/packages/proof/src/verify-proof.ts). They supply identity commitments, LeanIMT group operations and Groth16 membership proofs with message, scope and nullifier. The official [proof guide](https://docs.semaphore.pse.dev/guides/proofs) describes anonymous membership and repeat-use detection, not verified trader trustworthiness.

Mathematical `verifyProof()` success is insufficient. The proposed `packages/reputation/src/policy.ts` must authenticate root and issuer, define what score/credential admission represents, enforce expiry/revocation, bind the message to an action, and consume the nullifier under an explicit application/chain/epoch/action scope. A membership adapter belongs under the proposed `src/providers/`. Its result may later inform the arbitration trusted-snapshot port; it does not authorize changing that snapshot after randomness is requested.

Two concrete intake findings matter:

- The inspected [proof manifest](https://github.com/semaphore-protocol/semaphore/blob/dbab5553c486a09d5e1042e5271e3316224cc176/packages/proof/package.json) is 4.14.5 and pins `snarkjs` 0.7.5. That dependency's inspected `COPYING` is GPL-3.0. MIT at the top level is not a complete conclusion about distributing the proof bundle. This report does not decide compatibility or recommend replacing the engine without equivalent proof validation.
- `generateProof()` downloads artifacts when `snarkArtifacts` is omitted, with artifact version **4.13.0** in the inspected source. A package pin does not pin WASM, proving key, verification key and network behavior. Supply reviewed, checksum-identified artifacts through the qualified resource boundary; do not assume defaults meet proof-jobs budgets.

**Acceptance:** reject substituted roots, expired/revoked credentials under an explicit root policy, wrong message/scope and reused nullifiers; cover cross-action/chain/epoch binding; document recovery and root rotation; verify artifact checksums; measure low-end mobile proving behavior. A score circuit or issuer-backed threshold credential is separate work. Generic Noir/Circom frameworks would still need those missing semantics, so they are not presented as completed reputation features.

## Arbitration: reuse interfaces without changing custody semantics

### Kleros v2 and ERC-792

The current [`IArbitratorV2.sol`](https://github.com/kleros/kleros-v2/blob/38d778a4dd39606528c2b0725d0fff3f090aad30/contracts/src/arbitration/interfaces/IArbitratorV2.sol) is useful for dispute creation, fee quotations and ruling interface patterns. [`EvidenceModule.sol`](https://github.com/kleros/kleros-v2/blob/38d778a4dd39606528c2b0725d0fff3f090aad30/contracts/src/arbitration/evidence/EvidenceModule.sol) emits evidence references and has upgrade-related administration; it does not authenticate this repo's original NIP-17 messages or implement selective chat disclosure. [`DisputeKitClassic.sol`](https://github.com/kleros/kleros-v2/blob/38d778a4dd39606528c2b0725d0fff3f090aad30/contracts/src/arbitration/dispute-kits/DisputeKitClassic.sol) has concrete commit/vote, appeal-funding and outcome logic worth comparing with local models.

One material incompatibility: Kleros `hashVote(choice, salt)` uses a packed hash of those values. This project's `vote.ts` has a specific ABI Vote encoding and evidence-root binding with independent vectors. Substituting the upstream hash changes the protocol. Kleros appeal funding/court governance also do not equal the local one-appeal/fallback rules. Adapt failure scenarios and transition tests, not the protocol wholesale.

The older [`erc-792/contracts/IArbitrator.sol`](https://github.com/kleros/erc-792/blob/87bea72ec0a4c92ce7f62e596e84f24be7662dd7/contracts/IArbitrator.sol) provides concise arbitration/appeal method and event references. Its age and interface-only scope make it suitable as historical reference; the selected protocol must decide the actual ABI.

**Destinations:** new comparison fixtures beside `packages/arbitration/test/reference.test.mjs`; **NEW** `packages/arbitration/src/providers/kleros.ts` only for an explicitly selected external-Kleros option; **NEW** `contracts/optional/DisputeEscrow.sol` is a possible location for a separately designed native opt-in custody contract, not an existing/approved file. Upstream source cannot choose this project's certificate enum/tuple, case mapping, evidence-root encoding, release/refund rights or immutable deployed identity.

**Acceptance:** independent exact encoding vectors; wrong-case/round/evidence-root results rejected; basic trades cannot acquire tribunal rights without opt-in terms; deadlines/appeals use authoritative chain time; unauthorized rulings cannot release assets; fees/withdrawals, duplicate observations and reorgs reconcile with the transaction journal. These remain future integration obligations.

### Chainlink VRF v2.5

The inspected [`VRFConsumerBaseV2Plus.sol`](https://github.com/smartcontractkit/chainlink-evm/blob/982da1fb36c737664187c787fe5bfcba19d651a7/contracts/src/v0.8/vrf/VRFConsumerBaseV2Plus.sol) checks the configured coordinator in `rawFulfillRandomWords()` before invoking the consumer's callback. This is an authenticated-randomness integration pattern. It does not provide eligible jurors, frozen pools, missing draft-word domain/types, or payout policy.

**Destinations:** separately reviewed **NEW** `contracts/optional/JurorRandomnessConsumer.sol` and **NEW** `packages/arbitration/src/providers/chainlink-vrf.ts`, feeding the existing deterministic-word port. Pin the import closure, network/coordinator, consumer identity, subscription/funding, confirmation depth, request-to-case/round mapping and outage policy. These choices cannot be inferred from a provider logo or general interface.

Official [v2.5 security guidance](https://docs.chain.link/vrf/v2-5/security) directly informs acceptance: correlate fulfilments by request ID, choose confirmation policy, freeze outcome-affecting inputs before requesting randomness, prevent selective re-requesting, and keep callbacks from reverting. At review time that page also schedules v1/v2 shutdowns during November 2026; old VRF examples are unsuitable starting points.

**Acceptance:** independent draft-word vectors after domain/ABI specification; out-of-order/duplicate fulfilments handled; wrong coordinator/request/round rejected; frozen eligibility snapshot enforced; callback budget and outages tested; reorg-aware reconciliation; no discarding an unwanted random result to reroll. The existing bounded unbiased sampler can remain if its authenticated word source satisfies the chosen contract.

## Practical implementation order

1. **Resolve application contracts first.** Select one source/rail and exact receipt semantics for G29/G30; resolve a named stealth wire profile for G27; define issuer/root/score semantics for G28; specify arbitration evidence/certificate encodings and opt-in native custody.
2. **Create narrow intake records.** Suggested NEW directories: `security/intake/payment-evidence/`, `security/intake/semaphore/`, `security/intake/stealth-live/`, `security/intake/arbitration-provider/`. Record selected source, package/lock identity, full license text, imported files, transitive graph, artifact hashes, external authorities and explicit deferrals. This report is not an accepted intake.
3. **Build isolated fixture comparisons.** Retain existing diagnostic authority restrictions. The first deliverable should be independently verified interoperability and semantics, not a production toggle.
4. **Integrate only a qualified adapter.** Preserve immutable trade terms, explicit consent, local secret ownership, bounded resource lifecycle and transaction journal. Keep unselected alternatives as documentation rather than shipping every SDK.

The reusable portions are proof-verification machinery, membership proofs, ABI/event handling and bounded pagination. The largest remaining application work is the authority and meaning of a verified statement: its trusted source, exact claim, trade/action binding, revocation/finality handling, and whether a contract permits it to affect funds. None of the inspected repositories supplies that complete contract for P2P Offramp.
