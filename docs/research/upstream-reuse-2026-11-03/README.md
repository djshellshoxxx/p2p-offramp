# Unfinished-feature review and upstream code reuse research

Research snapshot: **2026-11-03 America/Vancouver / 2026-11-04 UTC**. This directory records source-based recommendations for completing P2P Offramp. It contains proposed integrations, not adopted dependencies, implementation receipts or release approval.

## Findings that determine the next work

**The highest-value work is finishing the existing EVM trade journey and its missing protocol/release contracts.** PR 26 already contains substantial local wallet, recovery, encrypted messaging, proof-job, locale and optional-feature machinery. New repositories can supply codecs, independent vectors, test tools, native program scaffolding and provider adapters. They cannot choose the missing peer-acceptance format, trust root, signed capability commitments, custody policy or payment-evidence meaning for this project.

The source review found three immediate integration defects or diagnosis tasks: dropped cancellation forwarding in `apps/web/src/app-services.ts`; action selection during recovery of a prepared, never-sent approval in `apps/web/src/journey/private-trade.ts`; and a reported browser resume-listener count mismatch whose owner still needs diagnosis. The first two are supported by inspected source; the listener failure is a prior reported result, not a reproduction. Their exact locations and narrowly scoped follow-ons are in [frontend quality](frontend-quality-reuse.md).

The production peer-acceptance carrier is still undefined. Existing `terms-accept` carries a revision; private agreement parsers/native checks remain test-only and do not authorize economic preparation. G14 negotiated capability fields also lack the exact mapping to G16's signed `{id, version, policyHash}`. These are distinct protocol tasks. See [Nostr and peer acceptance](nostr-privacy-reuse.md) and [escrow/release trust](escrow-release-arbitration-reuse.md).

The proof lifecycle is useful but does not yet have an operational production browser provider. In addition to the empty provider registry and missing proof/rail profile, the existing strict CSP refuses browser WASM compilation; physical worker-exit evidence currently uses a test-only CDP observer; production traffic accounting remains incomplete. A browser proof SDK is therefore conditional on an explicit architecture decision. See [payment proofs](payment-proof-reuse.md).

Native Solana is genuine implementation work: a terms encoder exists, but there is no qualified custody program, native wallet/read adapter or recovery path. The current SPL profile supports the reviewed original Token program; Token-2022 is not implicitly admitted. See [native Solana](solana-native-reuse.md).

## Recommended order of work

1. **Repair the current journey and integrate PR26 deliberately.** Recheck the current source, fix cancellation forwarding and prepared-approval recovery, diagnose the reported listener mismatch, and use the existing focused tests and browser runner for those changes. Review current CI/scanner results and the pending branch before integration. Preserve accepted local evidence; neither wholesale reimplementation nor optional-feature expansion resolves these defects. [Frontend findings](frontend-quality-reuse.md).
2. **Resolve D1, G14 and G15 as concrete protocol decisions.** Select the peer native-signature carrier, nonempty capability commitment mapping, and release/deployment/rotation/archive contracts with compatible reader/writer behavior and independent vectors. Reconcile off-chain consent with the actual escrow ABI. Upstream signing, canonicalization and trust-transition libraries are supporting components, not a choice of application authority. [Nostr](nostr-privacy-reuse.md), [trust](escrow-release-arbitration-reuse.md).
3. **Demonstrate the composed two-client EVM journey and recovery.** In the selected test environment, cover negotiated terms/native acceptances, funding, payment communication, seller release or expiry/refund, authoritative chain reconciliation and recovery independent of the original frontend. Exercise lock/reload, changed wallet/session, rejected signatures and unknown broadcast without automatic resend. Preserve old funded exits and evidence tied to the exact source/artifact. This is a future acceptance target, not a test result from this research.
4. **Then select bounded feature additions.** QR needs its payload contract first; proofs need source meaning and an executable host/profile; Solana needs native custody and token rules before tooling can establish parity. Optional maps, couriers, liquidity, arbitration, reputation and privacy providers should proceed only against the corresponding named remainder. Physical-device, language and production-release qualification remain separate evidence tasks. Draft PR27 proposes this core-first order; it is not a claim that all optional capabilities must be implemented to finish the core.

## How to adopt an upstream candidate

**A recommendation is not a dependency change.** Start with the exact missing behavior and existing target boundary. Prefer a small primitive, independent fixture generator or selected adapter over importing an upstream application's state, backend and custody model. Reuse current dependencies and completed intake where applicable. The relay harness already uses real sockets; `ws` intake records 6/6 cases, Waku retains a 13/14 codec result with a failure, and XMTP has completed passive comparison without a coherent runtime. These records must not become new generic intake tasks or be promoted beyond their stated scope. [Nostr/intake detail](nostr-privacy-reuse.md).

For each selected adoption, record the following:

- **Licensing and provenance.** Read actual license text, subpackage scope, copyright notices and generated/bundled dependency terms. The target has no general root LICENSE; BasicEscrow declares SPDX `UNLICENSED`. A permissively licensed upstream does not relicense the application or establish blanket compatibility. Retain required notices for copied code and inspect WASM/native artifacts separately. Same-owner sibling reuse still needs provenance and third-party notices. Conditional or conflicting licenses remain unresolved until the relevant scope is established. [License assessments](escrow-release-arbitration-reuse.md), [provider distinctions](payment-proof-reuse.md).
- **Exact version and integrity.** Pin the source commit/tag, selected package and lockfile, full dependency graph, toolchain and distributed artifact hashes. Compare the actual package bytes with the claimed source; registry integrity and unsigned `gitHead` are different evidence. XMTP's same-version source/package mismatch demonstrates why a manifest label is insufficient. Record what was verified and what remains unknown rather than substituting a newer default branch silently.
- **Architectural fit.** Keep the static core and external spending wallet. Do not move spend keys into the vault, add a required application backend, relax CSP, or bypass G05 endpoint/session ownership to accommodate an SDK. Account for workers, subrequests, storage, identity registration, cancellation and late results. If a provider cannot meet the selected boundary, keep it unsupported or propose a separately scoped architecture decision. [Proof-host constraints](payment-proof-reuse.md), [wallet integration](frontend-quality-reuse.md).
- **Meaningful validation.** Define the exact positive/negative compatibility cases and independent oracle before implementation. Preserve original bytes, domain/role binding, canonical amount/time encodings, replay behavior and fixed errors. Extend existing tests only for a demonstrated gap or changed profile, and retain genuine conformance failures. Separately measure the selected browser/device/runtime; a Node fixture, successful import, audit history or returned verification boolean cannot supply broader evidence.
- **Review and release disposition.** State whether the result is test-only, a source adaptation, an optional runtime candidate or rejected/deferred. Keep downstream authority unchanged unless its own contract is selected and reviewed. Source integration, provider qualification and artifact-specific release approval are different gates; keep `ReleaseEnabled: 0` and the absent approved pin until the actual release process supplies its required evidence. [Release boundary](escrow-release-arbitration-reuse.md).

## Method and limits

Three research agents worked in parallel with the root researcher, followed by focused assignments and independent cross-reviews. The team compared main, PR26 and PR27; read selected implementations, tests, intake records, protocol specifications and license files; and searched GitHub plus official project/platform documentation. Cross-review corrections include recognition of the existing socket harness, retained Waku failure, XMTP artifact mismatch, browser proof-host blockers and the limited meaning of upstream canonicalization helpers.

This work produced research notes only. **No product tests, project builds, provider executions, contract deployments, wallet signatures, bank-session requests or physical-device qualifications were performed for this review.** Previously recorded pass/fail outcomes belong to their cited earlier evidence; they were inspected, not rerun. Source pins, maintenance observations and source-level fit do not certify distributed binaries, audits or production readiness. Retrieval failures, renamed/archived repositories and unresolved license/profile questions are recorded in the relevant dossiers.

The table was checked against the actual ledger's `currentEngineeringState` field. It does not alter that ledger, its historical decisions or release state. Before implementing, reconcile the live head and close the specifically named gap; preserve accepted local work and its remaining limitations.
