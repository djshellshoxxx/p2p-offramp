# Optional maps, couriers, reputation, stealth and sibling-code reuse

Research date: 2026-11-03 America/Vancouver / 2026-11-04 UTC. Target: main `e9b9db3bfe9fd8ceb54f1eeebf481d82fd7a93aa`, with pending implementation inspected at PR 26 `94554ecf9854e4604f9f56afe5bebedeee931994`. This is an integration proposal, not evidence that optional features are enabled.

The current [remainder ledger][remainder] and the implemented [meetup](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/meetup/README.md), [courier](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/courier/README.md), [stealth](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/stealth/README.md), and [privacy controls](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/privacy-controls/README.md) distinguish working local models from missing production artifacts. The useful next steps are exact provider/native profiles, actual adapters and qualifying their integration.

Draft PR 27 proposes postponing optional implementation until the core two-client journey leaves LOCALPROOF. That is a [draft planning proposal](https://github.com/djshellshoxxx/p2p-offramp/blob/2f839b12768700ac6c3b674f75a144c6ec19fa93/docs/execution/NEXT-RUN-PROMPT-2026-11-04.md), not a merged restriction. These notes preserve concrete research for that later work.

## 3. Maps: the cache profile is the prerequisite

**Target:** existing `packages/meetup/src/map-manifest.ts`, `policy-data.ts`, `geofence.ts` and related tests. Proposed NEW renderer/cache modules belong beside this package and in the UI, with persistence through the established worker/storage boundary. Preserve the [map fetch policy][map-policy] and [tile cache specification][map-cache].

The cache requirement calls for a 100 MiB target and 2 MiB tiles, while [G02 vault schemas](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/schemas/src/vault.ts) cap each profile snapshot at 8 MiB and each record payload at 256 KiB. These are per-profile/record bounds, not a whole-origin quota. Existing small map-manifest/diagnostic evidence is not a completed tile cache. The storage profile must reconcile tile chunking, authenticated metadata, encryption, quota, eviction and deletion before claiming the larger cache. The signed manifest DTO also does not itself provide a fully selected remote-source/renderer resource contract. Do not invent a source URL field in an adapter and treat that as protocol approval. [Current implementation](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/meetup/src/map-manifest.ts), [remainder ledger][remainder].

PMTiles offers an injectable `Source` and local `FileSource`. Its URL constructor creates `FetchSource`, with its own fetching behavior; passing an approved-looking URL is insufficient. Prefer a local authenticated archive or a `Source` whose range reads use the existing transport broker, byte budgets and cancellation. Review compressed and decompressed byte limits separately. MapLibre rendering must account for style JSON, tiles, glyphs, sprites, workers and secondary requests, with no endpoint silently inherited from a demo.

The offline plugin's [database code](https://github.com/makinacorpus/maplibre-offline-pmtiles/blob/7cc2f4c2e81d3dbf99ba0476dc3f48308b3c082b/src/db.ts) and [PMTiles adapter](https://github.com/makinacorpus/maplibre-offline-pmtiles/blob/7cc2f4c2e81d3dbf99ba0476dc3f48308b3c082b/src/pmtiles_adapter.ts) are useful architecture references, but its direct fetch and raw OPFS storage do not preserve P2P's encrypted-vault and endpoint authority. Importing the plugin unchanged would introduce a second, unqualified storage/network stack. Its `clearAllStorage` enumerates and deletes the entire OPFS root; do not reuse that deletion method unchanged in an origin shared with other application data. A P2P cache adapter must own an explicit namespace and delete only its own records.

Use Turf and Proj4 first as independent distance/projection fixtures for existing geofence and tile-coordinate functions. Choose units, coordinate reference system and boundary tolerances explicitly. A valid coordinate or signed location claim does not establish real physical presence. `L-MEET-PROOF` and `L-MEET-PROOF-BINDING` need an exact proof source, statement, circuit/verification artifacts and trade binding; no map renderer supplies them.

**Acceptance:** authenticate archived tiles/metadata before use; enforce quota under cancellation and restart; dispose workers and renderer resources; demonstrate that no map resource bypasses transport policy; preserve redaction and bounded disclosure; verify deletion and offline behavior using the selected storage profile. Map-data attribution and licensing remain separate from renderer/codec licenses.

## 4. Couriers and lockers: select the actual vendor boundary

Existing [locker.ts](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/courier/src/locker.ts), accounting and custody modules already model local authorizations and outcomes. `L-CIT-LOCKER-LIVE` still needs a real device/vendor protocol; `L-CIT-COLLATERAL-CONTRACT` needs native collateral custody, withdrawal/slashing authority and accounting rules. The [locker command specification][locker-spec] is the integration anchor.

Matter's door-lock cluster is a concrete source to compare if the selected hardware supports it. It is native device/protocol code, not a browser driver to paste into `locker.ts`. Do not assume an arbitrary commercial locker supports Matter or that commissioning credentials belong in the static app. The selected vendor profile must describe an optional external device/bridge, authentication, command idempotency, acknowledgments, time windows and unknown outcomes while preserving the static core architecture.

**Acceptance:** a synthetic adapter can cover local state transitions; qualification needs the exact vendor/model/firmware and authenticated command/receipt contract. An acknowledgment must not automatically prove possession of cash or discharge economic obligations. Resolve cancellation, lost acknowledgment, expiry and manual recovery without automatic repeated physical actions. No hardware discovery, credentials, unlock command or transaction was attempted during this research.

For native collateral, reuse the existing contract/test infrastructure described in [the escrow dossier](escrow-release-arbitration-reuse.md). Another escrow implementation cannot choose who may slash, what proves an offense or how a courier exits. Those decisions precede native implementation.

## 5. Stealth: use independent vectors before copying code

Existing `packages/stealth/src/math.ts`, `profiles.ts`, `service.ts` and [DECISIONS.json](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/stealth/DECISIONS.json) already implement local derivation and scanning boundaries. The retained [comparison vectors](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/packages/stealth/test/fixtures/comparison-vectors.json) record an unresolved cross-encoding comparison. Preserve that result.

ScopeLift's SDK and the primary [ERC-5564](https://eips.ethereum.org/EIPS/eip-5564) / [ERC-6538](https://eips.ethereum.org/EIPS/eip-6538) specifications help settle shared-point serialization, hash input, scalar treatment, view tags, registry encoding and announcements. Code implementing an ERC profile is suitable only if the project's selected profile matches the exact bytes and math. A valid curve point alone does not establish interoperability.

The same-owner GhostPay [stealth implementation](https://github.com/djshellshoxxx/GhostPay/blob/0014bc5b26c7487ea1f9fb230194c36673193236/packages/core-crypto/src/stealth.ts) hashes a compressed shared point, reduces the hash modulo the curve order and rejects zero. The inspected P2P math rejects values outside the scalar range instead of using that reduction. This is a concrete behavioral difference, even if ordinary random samples rarely expose it. **Do not copy GhostPay stealth code as an interchangeable replacement.** Use deterministic comparison vectors and select a single documented scheme first.

`L-PRIV-STEALTH-SPEND` also needs an isolated ephemeral external-wallet capability, native spend/deployment/scan/finality rules and recovery. An announcer contract is not a private spending system; on-chain announcements remain public. Keep the current external-spending-wallet architecture. Importing an SDK does not authorize moving spend keys into the app vault. See the [spending specification][stealth-spend].

## 6. Reputation: reuse the completed Semaphore intake

The repo already contains [SEMAPHORE-V4-EVALUATION.md](https://github.com/djshellshoxxx/p2p-offramp/blob/94554ecf9854e4604f9f56afe5bebedeee931994/docs/reputation/SEMAPHORE-V4-EVALUATION.md), pinned evaluation scripts and retained observations. Resolve the reputation group/root/nullifier/revocation profile and integrate exact artifacts into `packages/proof-jobs`; repeating the same intake is not progress.

The inspected upstream generator fetches proving artifacts when the caller omits them. A P2P adapter must provide exact authorized artifacts through the existing bounded/cancellable resource path or reject the configuration. The verifier consumes group root, nullifier, message and scope-related public inputs. A group-membership proof does not establish a meaningful credit score, honest fiat payment, unique human or accepted root/revocation policy.

**Destination:** existing reputation specifications and `docs/execution/profiles/02-reputation.md` for the exact profile; a NEW narrow provider adapter behind `packages/proof-jobs/src/provider-boundary.ts` once selected. Preserve single-flight admission, worker memory/cancellation and unsupported-provider behavior. Acceptance needs matching public input vectors, root freshness, nullifier scope/consumption, revocation semantics and exact circuit/proving-key/verifier correspondence. The current CSP/WASM and physical worker-exit gaps described in [payment-proof reuse](payment-proof-reuse.md) also apply; existing test machinery is not a complete production browser provider port.

## 7. GhostPay QR: close structural fit, different payload profile

GhostPay's [assembler.ts](https://github.com/djshellshoxxx/GhostPay/blob/0014bc5b26c7487ea1f9fb230194c36673193236/packages/qr-exchange/src/assembler.ts), [camera.ts](https://github.com/djshellshoxxx/GhostPay/blob/0014bc5b26c7487ea1f9fb230194c36673193236/packages/qr-exchange/src/camera.ts), and [multipart.ts](https://github.com/djshellshoxxx/GhostPay/blob/0014bc5b26c7487ea1f9fb230194c36673193236/packages/qr-exchange/src/multipart.ts) fit this repository's explicit resource ownership better than a large wallet/share framework. Its package documents bounded multipart assembly at 32 KiB / 64 chunks and camera cancellation/cleanup. These are useful patterns, with tests/provenance to retain if ported.

P2P's [QR specification][qr-spec] caps the v1 envelope at 2,048 UTF-8 bytes and defers animated multipart. GhostPay's GPQ1 framing must not become P2P's profile by copying it. Prioritize selective camera-lifecycle adaptation and optical codec review; reserve multipart assembly for a separately approved future profile. A CRC or short session hash detects corruption/mixing under its defined assumptions; neither authenticates a sender nor authorizes an import, wallet connection or transaction.

**Proposed placement:** NEW `packages/qr/` pure codec/parser modules and a NEW app sharing camera controller, as detailed in [frontend quality reuse](frontend-quality-reuse.md). Keep type-specific validation/review in the existing authority boundary. Test late camera permission resolution after cancel, track disposal, stale frame suppression, duplicate callbacks, image/queue limits and restart behavior using synthetic inputs; qualify physical camera behavior separately.

P2P's existing [reuse ledger](https://github.com/djshellshoxxx/p2p-offramp/blob/e9b9db3bfe9fd8ceb54f1eeebf481d82fd7a93aa/docs/REUSE.md) records same-owner GhostPay reuse authority in its existing context. This report is not a new public license grant for GhostPay. For any selected port, record exact files/commit, modifications, ownership and third-party notices; retain the target's current licensing status. Third-party code keeps its obligations even when surrounding projects share an owner.
